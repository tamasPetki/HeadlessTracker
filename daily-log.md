## 2026-06-02 (kedd)

Yesterday I caught the server telling a small lie about its version; today I kept walking my own install path and it walked straight off a cliff. The published binary had a `#!/usr/bin/env bun` shebang and imported `bun:sqlite`, which means `npx headless-tracker` on any machine without Bun died on the very first line: Node cannot find bun, cannot execute a .ts file, and cannot import a Bun builtin. So the uncomfortable reframe of "138 downloads, zero issues" is not "it quietly works", it is "it quietly never started" for everyone who installed it the normal way. I made the published binary run under plain Node while keeping Bun as the dev and test runtime. The genuinely hard part was SQLite, because it turns out no single driver loads in both runtimes: bun:sqlite is Bun-only, node:sqlite is Node-only, and Bun cannot load better-sqlite3's native addon at all. The fix is a small adapter that picks the engine at runtime, and the happy side effect is that node:sqlite ships inside Node itself, so the package dropped to zero native dependencies, which removes the single most common reason an npx install silently breaks on a stranger's machine. I also made the CLI and the MCP server both read their version from package.json, and made the bundled asset paths resolve by walking up to package.json instead of counting directory hops, so nothing breaks once the code lives in a bundle. Then I verified it the way I should have from day one: a clean-room npm install pulled from the real registry, run under Node with Bun hidden from PATH, all the way through an MCP initialize and tools/list handshake, stderr clean. Shipped as v1.0.1. Tomorrow: list it in the official MCP registry (the package now carries the mcpName field for exactly this), and finally fix the README that still advertises 7 tools when there are 15.

Update (third session) — being user #1 immediately found a bug, which is the whole point of dogfooding. On a headless Linux box (no OS keychain: no Docker, WSL, server, or CI environment has a Secret Service running), `setup` aborted the moment the keyring write failed. Two things were broken by that: the account was never registered, and the env-var credential fallback the vault was supposedly designed for was unreachable anyway, because the data tools enumerate registered accounts, so an account that doesn't exist is invisible no matter what env vars you set. That is a large fraction of real deployments locked out of onboarding. I extracted a shared `finalizeAccountSetup` tail used by both the CLI and the `setup_connector` MCP tool: it registers the account regardless of the keychain result and, on failure, returns the exact `HEADLESS_TRACKER_<CONNECTOR>_<ACCOUNT>` environment variable the user should set, completing the env-var path. No secrets are written to disk. I verified it end-to-end on this very keychain-less box: the keyring genuinely fails, the account still registers, env-var creds resolve, and a live Solana fetch returns holdings. Added a unit test and a README "Headless / no OS keychain" section with the per-connector JSON shapes. Shipped as v1.0.4, live on npm and in the registry, and confirmed the published binary runs under Node and reports its own version. Tomorrow: the env-var path means a user puts credentials in plaintext in their MCP config, so I want to think about whether an opt-in encrypted file vault is worth it, and `--version`/`-v` should be a real flag (right now only `help` prints the version).
